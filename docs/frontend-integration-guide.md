# Frontend Integration Guide

This document describes the *flow* — the thing `/docs` (Swagger UI) and `/openapi.json` cannot
give you, because they document endpoints in isolation. Use Swagger for field-level detail
(request/response shapes, enum values, refusal responses); use this guide for the call sequence,
what drives your UI, and the two quarters that break the pattern (Q3's crisis, Q4's endgame).

**Every payload below is a real response, copy-pasted verbatim from
[`docs/examples/captured_payloads.json`](examples/captured_payloads.json)** — nothing here is
hand-typed. That file is regenerated by `uv run pytest tests/routes/test_capture_api_examples.py`
(part of the normal test suite) every time the schemas change, so it can never silently drift out
of sync with what the API actually returns. If a number below looks odd (e.g. `561.62` units
instead of a round number), that is the real, un-rounded Decimal the engine produced — round for
display, never for computation.

## 1. The lifecycle, as a call sequence

```
1.  POST /auth/register  (once)  ─┐
2.  POST /auth/login              ├─ get a Bearer token
                                   ┘
2b. GET  /companies                          -- runs you already own; skip to step 4 to resume one
3.  POST /companies                          -- start a run, become its owner
4.  GET  /companies/{id}/run                 -- read legal_moves; render the UI from it

    for each quarter:
5.    POST /companies/{id}/quarters                                    -- open it
6.    GET  /companies/{id}/run                                         -- re-read state
7.    POST .../quarters/{qid}/allocations/marketing                    ─┐
8.    POST .../quarters/{qid}/allocations/sales                         │
9.    POST .../quarters/{qid}/allocations/rnd                           ├─ the 6 departments,
10.   POST .../quarters/{qid}/allocations/operations                    │  any order, any count
11.   POST .../quarters/{qid}/allocations/hr                            │  of times each (upsert)
12.   POST .../quarters/{qid}/allocations/finance_admin                ─┘
13.   (Q3 only) POST .../quarters/{qid}/allocations/crisis              -- see section 4
14.   (Q4 only) GET  .../quarters/{qid}/endgame                         ─┐  see section 5
15.   (Q4 only) POST .../quarters/{qid}/endgame                         ─┘
16.   POST .../quarters/{qid}/lock                                      -- run the engine
17.   GET  .../quarters/{qid}/report                                    -- read the report

18. GET /companies/{id}/run          -- run_status is now COMPLETED or FAILED; only reads remain legal
19. GET /companies/{id}/leaderboard  -- optional: per-quarter score rollup
```

Steps 5-17 repeat once per quarter (the shipped scenario runs 4). There is no separate "start
Q2" call beyond re-opening the next quarter (step 5) — the engine carries every quarter's closing
state (cash, customers, Brand/Quality/Innovation Scores, ...) forward automatically.

**Step 2b — `GET /companies`, so a client never has to remember ids itself.** Ownership was
always enforced server-side, but until this existed nothing let you *discover* which company ids
you owned: lose your local copy and the run was unreachable forever, despite still being yours.
Returns every run owned by the caller, newest first, each with enough state
(`run_status`, `current_quarter_number`/`_status`, `quarters_locked`, `latest_ceo_score`/
`latest_band`) to render a "resume a run" list without a follow-up request per row. Strictly
owner-scoped — it is "my runs", never a directory of everyone's.

**Every route above appears in this flow except:**
- `GET /health` — infrastructure liveness check, not part of a run.
- `GET .../quarters/{qid}/crisis` — the crisis briefing; see section 4.
- `GET /companies/{id}` and `GET .../quarters/{qid}` — plain read-throughs of state you'll usually
  already have from `GET .../run` and a POST response; useful for a page refresh / deep link.
- The `finance`/`marketing`/`product`/`sales`/`cx` `.../decisions` and `.../state` routes — see
  section 6, "The legacy pipeline you probably don't need."

## 2. Authenticate

```
POST /auth/register  {"email": "student@myelin.dev", "password": "correct horse battery staple"}
POST /auth/login      -- same body, on return visits
```

Both proxy straight to Supabase Auth (password hashing and token signing are entirely Supabase's).
Response (`auth_login_response`):

```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.example-access-token",
  "email": "student@myelin.dev",
  "refresh_token": "v1.Mnb3-example-refresh-token",
  "user_id": "3fae5a10-4b2e-4f0a-8f0a-1c2d3e4f5a6b"
}
```

Send `access_token` as `Authorization: Bearer <access_token>` on every other request in this
guide. In Swagger UI, click "Authorize" and paste the token — the routes are already registered
against the `HTTPBearer` security scheme, so `/docs` will send it for you when trying requests live.

## 3. Start a run and read `legal_moves`

```
POST /companies  {"name": "Nadi Wear Capture Co"}
```

Response (`company_create_response`, trimmed):

```json
{
  "id": "2204ec72-1e8a-4532-b299-7635b3c413e3",
  "seq": 1,
  "name": "Nadi Wear Capture Co",
  "owner_id": "5c95a0ec-dd5a-4ef1-8062-d21a1250142e",
  "run_status": "active",
  "scenario": {"crisis_quarter": 3, "total_quarters": 4, "scenario_id": "nadi_wear_standard"},
  "quarters": []
}
```

`seq` is this owner's run number — their 1st, 2nd, 3rd run — assigned once at creation and
never reassigned. It is unique per owner, so a client can address a run as `/run/2` in its own
URLs instead of exposing the uuid, and resolve it back by looking the number up in
`GET /companies`. Every API path still takes `id`, and only `id`.

Now read run state (`GET /companies/{id}/run`) — this is the payload the entire UI should render
from, at every lifecycle point:

```json
// run_state_fresh
{
  "binding_constraint_hint": [],
  "company_id": "2204ec72-1e8a-4532-b299-7635b3c413e3",
  "crisis_quarter": 3,
  "current_quarter_id": null,
  "current_quarter_number": null,
  "current_quarter_status": null,
  "endgame_preview": null,
  "legal_moves": ["open_next_quarter"],
  "run_status": "active",
  "score_trajectory": [],
  "total_quarters": 4
}
```

### `legal_moves` drives the UI — do not hardcode it

**Do not hardcode which buttons are enabled at which lifecycle point.** `legal_moves` is the
gatekeeper's own answer to "what can this run legally do right now," computed fresh on every
read. Render your UI by checking membership in this array — `"submit_allocation" in legal_moves`,
`"lock_quarter" in legal_moves`, etc. — not by inferring it from `current_quarter_status` or
counting how many quarters have been opened. The move names are the exact values you'll also see
in `illegal_move`'s `attempted_move`/`allowed_moves` fields (section 7), so the same string
vocabulary works for both "what can I do" and "what did I just fail to do."

**The same payload at four more lifecycle points**, so you can see how `legal_moves` and the rest
of the shape change:

```json

  "current_quarter_number": 1,
  "current_quarter_status": "in_progress",
```

## 4. The quarter that's different: Q3 has a crisis

`crisis_quarter` (in every run-state payload) tells you *which quarter number* carries the
crisis — `3` for the shipped scenario. It does **not** tell you which of the four crisis
scenarios (Price Warrior / Marketing Blitz / Feature Leapfrog / Global Supply Shock, internally
lettered A-D) is live.

### `GET .../quarters/{quarter_id}/crisis` — what the student is told

*(This closes what earlier revisions of this guide listed as a known gap: the scenario letter used
to be recoverable only after lock, buried in `decision_quality.modifiers[].detail` strings.)*

Readable only in the crisis quarter (404 otherwise), and readable before, during and after the
response — it describes the event, not the student's answer to it:

```json
{
  "scenario_code": "C",
  "title": "Feature Leapfrog",
  "category": "competitive",
  "narrative": "Vantis has launched at Rs 10,499 -- pricier than you -- but with genuinely superior specs. The threat is entirely about product credibility.",
  "choices": [
    {"code": "D", "label": "Contract R&D Sprint",
     "effect": "Rent outside engineering capacity for one quarter. Raises Innovation Score now, though less per rupee than building the same capability in-house."}
  ],
  "response_lines": [{"field": "crisis_choice_d_spend", "label": "Choice D spend"}],
  "ignoring_is_legal": true
}
```

**`response_lines` is the field that makes this worth calling.** The crisis allocation request
accepts five spend lines, but each scenario's recovery formulas read only a subset — Feature
Leapfrog, above, has no documented recovery for its dampening or conversion penalty at all, so
every rupee outside its Choice-D line is inert. Render the full five-field form to everyone and a
student can spend their whole response budget on a line that does nothing. Drive the form from
`response_lines`, and the choice menu from `choices`.

**What it deliberately never returns is a number.** No coefficient, threshold, penalty magnitude
or multiplier appears anywhere in the payload — `docs/11-crisis-system.md` §2 is explicit that
students are told the narrative and the choices but "must diagnose their specific situation from
their own quarter's results." The report they read *after* locking is where the numbers live.

### The crisis-response allocation

`POST .../quarters/{quarter_id}/allocations/crisis` — a 7th allocation line, legal *only* in the
crisis quarter (`submit_crisis_allocation` in `legal_moves`; attempting it elsewhere returns
`illegal_move`). Request (`crisis_allocation_submit_request`):

```json
{"crisis_choice": "C", "comparison_ads": "5.0", "emergency_supply_fund": "1.0"}
```

Fields: `crisis_choice` (`"A"`/`"B"`/`"C"`/`"D"`/`null`), `price_match_fund`, `comparison_ads`,
`retention_offers`, `emergency_supply_fund`, `crisis_choice_d_spend` — all Rs lakhs, all
independently optional. Only the fields relevant to whichever scenario actually fired have any
effect; the rest are harmlessly ignored (this run picked Choice C and spent on two lines that
weren't the dominant lever for its assigned scenario — see below).

**`crisis_choice` is a different letter axis than the crisis scenario.** Scenario B's own Choice A
means something different from Scenario A's Choice A. Don't conflate "which scenario fired" with
"which choice the student picked" — both are single letters A-D, but on independent axes.

**Ignoring the crisis is a legal move, not a rejected one.** Submitting `{}` (every field at its
zero default) is accepted exactly like any other allocation — it's simply penalised: the report's
`decision_quality.modifiers` will include a fired `crisis_ignored` line (−4). This run's report
(`quarter_report_q3_with_crisis`) shows what that penalty explanation looks like, and confirms the
scenario letter is only recoverable from this text:

```json
{
  "id": "crisis_fully_neutralized",
  "detail": "crisis_scenario=B, crisis_fully_neutralized=False"
},
{
  "id": "crisis_ignored",
  "detail": "crisis_scenario=B, crisis_response_spend_inr=Rs 500,000.00, fully_neutralized=False, proofed_by_prior_investment=False"
}
```

(This run spent Rs 5,00,000 on Comparison Ads and the Emergency Supply Fund — the Scenario D/A
levers — against an actual Scenario B event, so it counted as spend but didn't neutralize the
crisis; `crisis_ignored` still didn't fire because spend was nonzero. `outcome.net_cash_flow_inr`
for this quarter was `-Rs 10,37,406.59`.)

## 5. The quarter that's different: Q4 has an endgame

Once `current_quarter_number == total_quarters`, `GET .../quarters/{quarter_id}/endgame` becomes
legal (`read_endgame_preview` in `legal_moves`) and `run-state`'s `endgame_preview` populates —
see the Q4 panel in section 3. No decision is required to *see* the preview: the tier and every
number in it are a pure consequence of Q1-Q3's already-locked results.

**Tier** (`thriving` / `stable` / `distressed`) decides the three-item **term-sheet menu**:

```json
{"path_a_name": "Rescue Financing", "path_b_name": "Fire-Sale", "path_c_name": "High-Risk Independent"}
```

**Three paths, always labelled A/B/C:**
- **Path A** — continue independently, committed to a units-sold covenant (`covenant_units`).
- **Path B** — accept an offer, referenced against `true_continuation_value_inr`
  (`acquisition_trap_offer_inr` is only a concrete number for the Thriving tier's specific
  Acquisition Trap term sheet; it's `null` for every other tier/term-sheet combination — no
  source-stated formula exists for those yet, so the backend refuses to invent one).
- **Path C** — stay independent, no covenant attached.

### Submitting the decision

```
POST .../quarters/{quarter_id}/endgame
```

Request (`endgame_decision_submit_request`) — `term_sheet_name` must match one of the three names
from the preview's menu for this tier:

```json
{"path": "C", "term_sheet_name": "High-Risk Independent", "reasoning": "staying independent based on the Q1-Q3 trend"}
```

Legal only before Q4 locks; upserted (call it again to change your mind). The outcome (covenant
hit/missed, offer accepted/declined) is scored at `POST .../lock`, not by this endpoint.

### The final report

Once Q4 locks, its `QuarterReportResponse.run_summary` is populated (only ever true on the
terminal quarter of a COMPLETED or FAILED run):

```json
{
  "final_valuation_inr": "97809385.32657556514429693318",
  "score_trajectory": [
    {"quarter_number": 1, "ceo_score": "55.26", "band": "Weak"},
    {"quarter_number": 2, "ceo_score": "42.74", "band": "Weak"},
    {"quarter_number": 3, "ceo_score": "73.68", "band": "Competent"},
    {"quarter_number": 4, "ceo_score": "76.68", "band": "Strong"}
  ],
  "terminal_status": "completed"
}
```

`run_summary` is just the aggregation of quarters that already exist — it carries no Q4-specific
content (tier, term sheets); read that from `endgame_preview` on the same `GET .../run` call
instead.

## 6. What state the client holds vs. re-fetches

**The server is the source of truth for game state; the client renders it, never computes it.**
Concretely:

| Value | Cache it? | Why |
|---|---|---|
| A locked quarter's `QuarterReportResponse` | **Yes, indefinitely** | Never recomputed once written — `report_service` only ever reads back what `POST .../lock` persisted. Re-reading it twice is guaranteed byte-identical. |
| `legal_moves` | **No — re-fetch after every write** | Recomputed fresh on every `GET .../run`; a write you just made changes it. |
| `endgame_preview` | **No** | As shown in section 3's last panel, it can genuinely change between reads (it re-derives tier from current survival state each time) even with no new write from you. |
| `QuarterDetailResponse.allocations` (submitted-so-far spend) | **No, while the quarter is open** | Every `POST .../allocations/{department}` upserts; re-fetch after each submission if you show a running total. |
| A company's `owner_id`, `scenario`, `seed_name`, `profile_name` | **Yes** | Fixed at creation. |

If in doubt: re-fetch `GET .../run` after every write. It is cheap (one read, no computation) and
is always correct.

## 7. Reading the two-part report

`QuarterReportResponse` deliberately keeps two sections structurally separate — **never render
them as if one implies the other.** A student can lose money and score well, or make money and
score badly (see the Q1 example below, and `docs/15-q3-noob-vs-expert.md`'s Scenario D pair for
the most extreme case: the novice earned more cash yet scored 26 points lower for banking a
short-term gain over a permanent capability).

### `outcome` — "what happened to the company" (business fact, no judgment)

```json
{
  "units_sold": {"value": "561.62...", "delta": null},
  "revenue_inr": {"value": "5615653.10...", "delta": null},
  "cogs_inr": {"value": "1733448.54...", "delta": null},
  "gross_profit_inr": {"value": "3882204.56...", "delta": null},
  "net_cash_flow_inr": {"value": "-3127836.80...", "delta": null},
  "closing_cash_inr": {"value": "11872163.19...", "delta": null},
  "cash_runway_quarters": {"value": "3.79...", "delta": null},
  "valuation_inr": {"value": "52507746.33...", "delta": null}
}
```

Every metric is `{value, delta}` — `delta` is `null` on Q1 (no prior quarter), never `0` (which
would misreport "no change" for a number with no history yet). Render deltas as
up/down indicators once available.

`binding_constraints` (0-3 entries; can be empty — that's a genuinely good outcome) names which
hard gate(s) actually limited this quarter, in plain language:

```json
[
  {"gate": "sales_capacity", "demand_lost": "216.48...", "demand_lost_unit": "leads",
   "detail": "Sales Capacity (2725.0000 effective) bound 216.48... leads' worth of demand..."},
  {"gate": "conversion_ceiling", "demand_lost": "8.14...", "demand_lost_unit": "conversion_points",
   "detail": "the Conversion Ceiling (19.10...%) capped 8.14... points of raw conversion..."}
]
```

### `decision_quality` — "how good were these decisions" (built from the score alone)

```json
{
  "ceo_score": "55.26",
  "band": "Weak",
  "mechanical_points_available": "31.66...",
  "unscored_points": "68.33...",
  "modifiers": [...],
  "scored_criteria": [...],
  "unscored_criteria": [...]
}
```

**`ceo_score`/`band` are the scoreable-portion, normalised score — labelled as such, not the
complete 21-criterion rubric.** Only 6 of 21 rubric sub-criteria are MECHANICAL (formula-derived)
today; the rest are JUDGMENT and require human/LLM review the engine doesn't perform. Render this
honestly:

- **`modifiers`** — named point adjustments (e.g. `perfect_channel_match`, `crisis_ignored`), each
  with `fired`/`applied_points`/a `detail` string explaining the numbers behind the decision:
  ```json
  {"id": "perfect_channel_match", "points": "2", "fired": true, "applied_points": "2",
   "detail": "referral leads=800.00, referral_lead_cap=800.00, referral_wasted_spend_inr=0.0000"}
  ```
- **`scored_criteria`** — the 6 MECHANICAL sub-criteria that actually scored, each with a
  `result` (`"clearly_met"` full trait-weight share / `"partially_met"` half share / `"not_met"`
  zero) and a `detail` explaining the numbers.
- **`unscored_criteria`** — the 15 JUDGMENT sub-criteria, each with a `reason`, **never a zero and
  never hidden** — a zero would read as a failure the student didn't earn:
  ```json
  {"id": "systems_thinking_1", "trait": "systems_thinking",
   "reason": "'Correctly identified' asks about the student's stated understanding of the dependency, not just its numeric consequence -- the consequence is checkable (systems_thinking_2/3 do), the identification claim is not."}
  ```

  **Render `unscored_criteria` as "not yet assessed," never omit it and never show 0/100 as if
  every criterion had a mechanical answer.** This is the single most important rendering rule in
  this guide: a UI that silently drops `unscored_criteria` or folds it into a lower score
  misrepresents what the engine actually knows.

### `evidence` — a separate, honest observation log

```json
"evidence": {
  "capital_allocation": [{"department": "finance_admin", "evidence_key": "finance_cash_preservation",
    "detail": "pre-revenue margin = ... = Rs 7,150,000.00 (buffer_preserved=True); ...", "value": {"...": "..."}}],
  "leadership": [{"department": "hr", "evidence_key": "hr_culture_investment",
    "detail": "Culture & Benefits funded: Employee Satisfaction now 70.47...", "value": {"...": "..."}}],
  "...": "systems_thinking, risk_management, strategic_thinking, long_term_thinking"
}
```

Keyed by cognitive-dimension category (matching the 7 CEO-score traits). Populated automatically
at lock time from the same 22-line allocations that produced `outcome` — no separate submission
needed. Render each entry as an *observation*, never a grade: this pipeline is intentionally
independent of `decision_quality` (CLAUDE.md: "Two pipelines stay independent. Business Impact
and Evidence are separate").

## 8. Errors a client must handle

Every refusal is a distinct, machine-readable shape — check `response.status` first, then the
body's `error` key (401/403/409) or `detail` (404/other 409s).

| Status | `error` | Meaning | UI action |
|---|---|---|---|
| 401 | `not_authenticated` | No valid Bearer token. | Send the user to login. |
| 403 | `not_permitted` | Authenticated, but not this run's owner (writes) or not owner-or-instructor (reads). | Show "not your run" — do not retry. |
| 409 | `illegal_move` | Well-formed and permitted, but not legal in the run's current state right now. | Re-fetch `GET .../run`, re-render from its `legal_moves`/`allowed_moves`. |
| 409 | *(plain `detail`, no `error` key)* | A route-specific ordering conflict, e.g. "report requested before the quarter locked" — not the gatekeeper's envelope. | Same as above: re-fetch and re-render. |
| 404 | *(plain `detail`)* | The company/quarter doesn't exist (bad id, or a typo in the URL). | Show "not found" / navigate back. |

Captured examples:

```json
// 401 -- error_not_authenticated
{"error": "not_authenticated"}

// 403 -- error_not_permitted
{"error": "not_permitted", "reason": "user 4254ea22-2085-4f7a-a6b2-84ebc223ff14 may not view company 2204ec72-1e8a-4532-b299-7635b3c413e3"}

// 409 -- error_illegal_move
{
  "error": "illegal_move",
  "attempted_move": "open_next_quarter",
  "reason": "the run is completed; a terminated run accepts no further submissions or locks",
  "allowed_moves": ["read_endgame_preview", "read_quarter_report"]
}

// 404 -- error_not_found
{"detail": "Company 50835e7b-ed2e-4739-88f7-ee1751ac5336 not found"}
```

`illegal_move`'s `allowed_moves` is exactly what the same run's `GET .../run` would return in
`legal_moves` at that instant — a client can re-render its UI from the error response alone,
without a second request, then confirm with a real `GET .../run` on next render.

---

## 9. The legacy pipeline you probably don't need

`finance`/`marketing`/`product`/`sales`/`cx`'s `.../decisions` and `.../state` routes are a
**separate, older per-decision system** (CLAUDE.md's ~72-key decision taxonomy), not part of the
22-line allocation flow this guide otherwise describes. They write their own `Decision`/`Evidence`
rows that **never** appear in a quarter report — `outcome` never reads them, and the `evidence`
dict is fully populated by the 22-line allocations alone (section 7). Operations and HR have no
equivalent routes at all (no decision spec exists for them; see
`docs/10-implementation-gaps.md`).

Unless your product specifically wants the legacy per-decision UI surface, skip this section of
the API entirely — the full lifecycle in section 1 works without ever calling it.

## 10. Cross-check: every endpoint accounted for

Every route in `/openapi.json` appears in this guide's flow (section 1, its crisis/endgame
specials in sections 4-5, or read-throughs noted alongside it) or is explicitly named as
out-of-flow: `GET /health` (liveness only) and the 15 legacy per-workspace routes (section 9).

**`GET /companies/{id}/leaderboard` reports `ceo_score`/`band`** — the same two numbers
`score_trajectory` and `decision_quality` carry, for each quarter that has locked. It previously
returned an `overall_score` field belonging to the legacy per-decision cognitive pipeline, which
`run_quarter()` never invokes; that field was therefore `null` for every quarter of every run the
shipped 22-line flow produces, and has been removed rather than left reporting a permanent null
as though it were a score. An open quarter has no rollup row yet and is simply absent from
`entries`, rather than present with a null score.
Every enum a client branches on — `run_status` (ACTIVE/DISTRESSED/FAILED/COMPLETED), quarter
`status` (IN_PROGRESS/CLOSED), `legal_moves`/`Move` values, crisis `crisis_choice`
(A/B/C/D/null), Q4 `tier` (THRIVING/STABLE/DISTRESSED) and `path` (A/B/C) — is documented both
here (with what each value means for your UI) and in Swagger (as a typed enum on the relevant
schema, so a generated client gets it for free).
